The situation

Game updates depended on people doing every step by hand. Each new game version had to become tickets, tasks in a tracking system, for every market. Each ticket then had to be scheduled, linked to related work, tracked on a project board and reported back to the person who asked. Automating that created a bigger risk: a job could fail quietly while the dashboard said all was well.

What I owned: process automation

I owned the automation of the update process, from request to close-out, and the audit that checked whether it did. I designed and built the automations myself, writing the code with help from AI tools.

The decision: issue containment

When I found a scheduling job doing nothing while the dashboard showed it as healthy, I paused all the automations rather than let silent failures keep running on the live pipeline. "Healthy" only meant "ran without crashing". It did not mean the job had done its work.

I also left rescheduling clashes to people rather than automate them. When two pieces of work clash, choosing which moves is a judgement call, not a rule.

How I ran it: risk mitigation and controls

  • Built the base. I built 24 automated jobs in Python, a programming language. They run on a schedule and connect to Jira, our ticket system, and Monday.com, our project board. They took over creating tickets, scheduling, linking, updating the board, tracking status and replying to the people who made requests.
  • Joined it into one flow. In June 2026 I built one automation that handles every step of a game update, from start to finish. It runs twice each weekday. For monitoring and control, a control screen on my own machine shows the work in progress, the calendar, the automations and alerts. It records every action and checks itself each time it starts.
  • Set a trust control. I built a view-only mode so a reviewing team could trust the system without running it.
  • Ran the audit. I checked all 16 programs and, through root cause analysis, grouped the problems into three kinds of bug: errors counted as success, names matched too loosely, and failed work marked as done. I prioritized the riskiest programs and fixed them first.
  • Added safeguards. I added a daily health check, and safeguards against duplicate tickets in 7 processes.
  • Cleaned up leftovers. I cleaned up 1,220 leftover tickets with nothing linked to them. An older automatic rule built into the tool had left them behind.
  • Closed finished work automatically. In July 2026 I launched an automation that closes out finished work. Its first real run moved 21 records, and I checked each one.
  • Fixed the cause. In August 2026 I found 7 games with 28 duplicate tickets. 11 of them were scheduled in the wrong order, a release management risk: an older version of the game would go out last. I cancelled all 28 and checked them. As a process improvement, I then changed the automation so it cancels the old ticket itself and moves its date to the new one.

The result

  • The audit surfaced 170 error messages, 165 failure messages and 15 crash reports that had been hidden in the system's logs.
  • 1,220 leftover tickets cleaned up, and 28 duplicate tickets cancelled.
  • Quality control: a second close-out run checked 520 child items, smaller tasks that sit under a main item, and closed 170, with 0 errors.
  • A daily health check now runs on the schedule alongside the automations.
  • Rescheduling clashes stay with people, by design.
